# 仓库敏感信息核查技能

> 一句话方案：**四层扫描证明"没有凭据"，再逐通道核对"凭据从哪来"，最后按"秘密 / 业务信息 / 公开标识"三档给出公开与退役结论。**

## 1. 两条铁律（先记住，再动手）

1. **只扫工作区 = 没扫。** git 历史会保留一切，一旦仓库公开，历史里的内容永久可检索。
   已 push 的内容**删不掉**（除非重写历史）。所以核查必须覆盖 `git log --all -p`。
2. **凭据不在代码文件里就等于安全** —— 这是错的。真实泄密点常在这些位置：

   | 位置 | 为什么容易被忽略 |
   |---|---|
   | Markdown 文档里的示例 | 人们只扫代码，不扫 `.md`；示例常从真实值复制而来 |
   | JSON / YAML / JSONL 配置 | 常被当作"配置"而非"代码" |
   | 注释与 docstring | `# AK = "..."` 这种临时记录 |
   | 未跟踪文件（`??`） | 本地调试留下的 `.env`、`*.pem`；一旦 `git add -A` 就进去了 |
   | 打包产物 / 示例文件（`*.example`） | 从真实文件复制时忘记替换 |

## 2. 四层扫描（逐层执行，缺一层就不能下结论）

| 层 | 目标 | 工具 |
|---|---|---|
| L1 已知凭据格式 | 主流平台的密钥指纹 | `scripts/Scan.ps1` |
| L2 高熵长字符串 | 不匹配已知格式的自定义密钥 | `scripts/EntropyScan.py` |
| L3 git 全历史 | 曾经提交过、后来删掉的凭据 | `scripts/Scan.ps1 -History` |
| L4 未跟踪凭据文件 | 本地凭据文件与 `.gitignore` 覆盖 | `scripts/Scan.ps1 -LocalFiles` |

### 2.1 L1：已知凭据格式

覆盖：AWS Access Key、GitHub PAT（classic / fine-grained / OAuth）、JWT、OpenAI 风格 `sk-`、
Supabase PAT `sbp_`、Slack `xox*`、Google `AIza`、PEM 私钥头。

```powershell
# Windows PowerShell 5.1 与 PowerShell 7 都可用；本机若无 pwsh 就用 powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Scan.ps1 -Root <仓库根>
# PowerShell 7+ 可简写：pwsh -File scripts/Scan.ps1 -Root <仓库根>
```

**已知误报**（必须人工确认，不要直接改代码）：

- PEM 私钥头常命中**文档里讲解 PEM 格式的文字**（把标记写在反引号里的说明句），不是真钥；
- 安全类技能/文档自身若写了完整示例密钥串（如 AWS 官方样例），也会被扫中 ——
  **写文档时应把示例截断或加掩码**，否则技能会持续给自己制造噪声。

### 2.2 L2：高熵长字符串

L1 只能发现"标准形状"的密钥。自研系统的 token 往往没有固定前缀，靠熵与长度识别。

```powershell
python3 scripts/EntropyScan.py <仓库根>
```

**设计要点（这个脚本本身踩过坑，别简化掉）**：

- **必须过滤噪声**，否则满屏是 `====`、`--------`、路径、标识符 —— 噪声一多就会漏看真命中。
- **要过滤"参数名/函数名"这类伪命中**：`privateKeyText=privateKeyText`、
  `ed25519PublicKeyFromSeed`、`include_system_vars=True` 都不是凭据。有效判据是：
  ① token 位于 `=` 右侧（左侧是赋值目标/形参名）；② token 含数字；
  ③ 长度与熵达标。三条同时满足才作为候选。
- **跳过纯注释行**：注释里的说明文字不是凭据。
- **输出必须截断**。**扫描工具自身绝不能回显完整疑似凭据** ——
  否则工具的输出、日志、CI artifact 就成了新的泄露面。
- **必须做反向验证**（`scripts/VerifyFilters.py`）：用随机生成的**真实密钥样本**确认
  过滤规则**零误拦**。这是本层最重要的纪律 —— 为提高信噪比而加规则时，极易顺手把
  真实密钥也滤掉，而"扫了但没看见"（假阴性）远比"扫出一堆噪声"严重。
  实测数据：加过滤前 107 处候选，加过滤后 12 处；反向验证 8 类真实密钥全部放行、
  12 类伪命中全部拦截。

```powershell
python3 scripts/VerifyFilters.py     # 改过过滤规则后必跑
```

- 本层是**启发式**，命中 ≠ 泄密。逐条人工判断，重点关注：赋值语句右侧、`key=`/`token=` 之后的长串。

### 2.2.1 核心纪律：过滤用"必要条件"，降权用"版式特征"

这是本技能最重要的一条经验，**用实测代价换来的**：

| 判据 | 用法 | 理由 |
|---|---|---|
| 长度 ≥ 24 | **过滤** | 随机密钥几乎必然满足；短串本就无密钥空间 |
| 明确噪声形态（分隔线 / 路径 / MIME / 域名） | **过滤** | 这些不可能是凭据 |
| 位于 `=` 右侧 | **过滤** | `名=同名实参` 是赋值目标，不是值 |
| 含数字 | **过滤** | 无数字的自研密钥概率 <1%，可接受 |
| 长纯 hex（≥32 且熵≥3.5） | **放行** | hex 编码的密钥极常见 |
| 全大写常量名 / camelCase 版式 / 版本号数字块 | **只降权** | ⚠️ 见下 |

**为什么版式特征不能用来过滤**：随机密钥里出现"标识符特征"的概率并不低。
实测把 camelCase 判据调松 → 放行标识符噪声；调紧 → **随机密钥误拦率升到 25%**
（自检 5 次里出现 1 次失败）。而**假阴性（扫了但没看见）远比噪声危险** ——
噪声只是报告长一点，假阴性意味着"以为扫干净了，其实漏了真钥"。

**结论：`identifierScore` 只参与排序（把标识符排到报告后部），绝不参与过滤。**
自检脚本的退出码因此**只由假阴性决定** —— 若把噪声也算失败，会诱使后续维护者
继续收紧规则，把假阴性重新引回来。

**判据设计中被推翻的尝试（留档，避免重复踩坑）**：

| 曾用判据 | 被推翻的原因 |
|---|---|
| 出现连续大写 `[A-Z]{2,}` 即判标识符 | 32 位字母密钥里出现连续大写概率 ≈30%，**误拦 2/8 真实密钥** |
| 下划线分段且各段大小写同构即判标识符 | `sk_live_<hex>_<hex>` 各段恰好同构，被系统性误拦 |
| 所有纯 hex 一律当噪声 | **误拦 hex 编码的密钥**（hex 是最常见的密钥编码之一） |
| 长数字块判据放在密钥前缀之前 | hex 密钥里 4 位连续数字极常见（`...9012...`），顺序反了就误拦 |

### 2.3 L3：git 全历史（**最容易漏的一层**）

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Scan.ps1 -Root <仓库根> -History
```

同时做一次针对性检索，确认历史上从未出现过长密钥/JWT：

```powershell
git log --all -p --pretty=format:'COMMIT:%h %s' |
  Select-String -Pattern 'eyJ[A-Za-z0-9_-]{30,}|apikey["'']?\s*[:=]\s*["'']?[A-Za-z0-9_\-\.]{40,}'
```

> PowerShell 引号嵌套易出错，建议直接用 `scripts/Scan.ps1 -History`（已封装该检索）。

### 2.4 L4：未跟踪凭据文件与 `.gitignore`

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Scan.ps1 -Root <仓库根> -LocalFiles
```

检查项：

- 存在 `.env` / `*.pem` / `*.key` / `*secret*` / `*credential*` / `*token*` / `*password*` 文件吗？
- `.gitignore` 是否覆盖 `.env` 与 `.env.*`（同时保留 `!.env.example` 以便提交模板）？
- 这些文件**当前是否已被跟踪**（`git ls-files`）？已跟踪就必须从索引移除，光加 `.gitignore` 无效。

```powershell
git ls-files | Select-String -Pattern '\.env$|\.pem$|\.key$|secret|credential'
```

## 3. 凭据来源逐通道核对（比扫描更重要）

扫描只能证明"已提交的内容里没有凭据"。**真正的设计问题是：凭据从哪来。**
逐通道确认下表，任一通道出现"硬编码"或"从仓库内文件读取"就是设计缺陷：

| 通道 | 期望形态 | 判定 |
|---|---|---|
| 环境变量 / CI Secrets | 代码只 `os.environ.get(...)` / `process.env.*` | ✅ 正确 |
| 仓库内文件（`*.json` / `.env` / `*.pem`） | **不应存在** | ❌ 立即整改 |
| 代码内默认值 | **不应有非空默认密钥** | ❌ 立即整改 |
| 命令行参数 | 可选，且**不得写入日志** | ⚠️ 需确认日志脱敏 |
| 日志 / 异常信息 | 不得打印凭据原文 | ⚠️ 需确认 |

检查命令：

```powershell
# 凭据只应来自环境变量：列出所有凭据相关读取点
Select-String -Path <代码目录>\*.py -Pattern 'environ\.get\(|getenv\(|ENV_[A-Z_]+ ='

# 反向检查：是否有读取仓库内文件当凭据的路径（设计缺陷信号）
Select-String -Path <代码目录>\*.py -Pattern 'open\(.*\.json|load_dotenv|load_commit_config|\.pem|ReadAllText'
```

## 4. 信息分级：不是所有"看起来敏感"的都算泄密

扫描常会命中大量非凭据内容。按三档判定，避免过度反应也避免漏判：

| 档 | 例子 | 判定 |
|---|---|---|
| **秘密**（泄露即风险） | `service_role` key、私钥、PAT、连接串密码 | 必须清除；已 push 需评估重写历史 |
| **公开标识**（设计上可见） | Supabase `project ref` 与 `anon` key、公开 API 域名、仓库 owner/repo | 可保留；但会暴露后端形态，按需收口 |
| **业务信息**（非凭据但属内部） | 存储桶名与 endpoint、对象存储 `CID`、内部回调 API 路径、表结构、定时任务节拍 | **由所有者决定**；转公开仓库前应逐项过一遍 |

> 实践提醒：**转公开仓库时，既有文件的暴露面往往大于新增文件。** 新增代码通常已经过脱敏，
> 而历史遗留脚本里可能有内部回调路径、桶名、项目标识 —— 核查要覆盖全仓库，不能只看本次改动。

## 5. 退役条件判定（文件能否删除）

对每个候选退役文件，回答三个问题：

1. **生产链路还依赖它吗？** 用可执行方式确认，别靠印象：
   ```powershell
   # 依赖应已内联/移除时，确认无残留引用
   Get-ChildItem -Recurse -File <目录> -Include *.py,*.yml,*.md |
     Select-String -Pattern '<文件名>'
   ```
2. **还有谁引用它？** 特别检查**校验器、构建脚本、文档、CI** —— 这类"间接引用"最容易漏。
3. **删掉会失去什么能力？** 例如：某文件是"比对基准"，删掉后一致性校验会降级为"跳过"。

**退役处理策略**：

| 情形 | 处理 |
|---|---|
| 生产已不依赖，仅校验器/文档引用 | 可退役；同步修改引用点，或把校验降级为显式"跳过并告警" |
| 需要保留比对能力但又不想留第二份副本 | 只保留**指纹**（sha256），校验器改为比对指纹 |
| 内容已被内联到别处 | 先确认内联副本逐行一致，再退役来源 |

## 6. 输出结论模板

核查报告按此结构给出，避免"感觉安全"这种无效结论：

```markdown
## 一、凭据层面结论
L1 已知格式：<N 命中 / 逐条说明误报>
L2 高熵串：  <命中数与人工判断>
L3 git 历史：<从未出现 / 发现于 commit xxx>
L4 本地文件：<无 / 列出>
→ 凭据泄露判定：干净 / 存在风险（列具体项）

## 二、会被公开的内容（按风险排序）
| # | 内容 | 位置 | 风险 | 建议 |

## 三、退役条件
<文件> → 可退役 / 有牵连（列出引用点）/ 建议指纹方案

## 四、需要所有者确认的前提
- 仓库当前是公开还是私有？（决定是否需重写历史）
- 业务信息（桶名/内部路径/表结构）是否属可公开范围？
```

## 7. 常被忽略的坑（都是实际踩过的）

1. **只扫工作区不扫历史** —— 最严重的漏判来源。历史里删掉的凭据依然可检索。
2. **`git add -A` 把未跟踪的敏感文件一并提交** —— 批量暂存前先 `git status` 看清单。
3. **以为加了 `.gitignore` 就安全** —— 已跟踪文件不受 `.gitignore` 影响，必须
   `git rm --cached`。
4. **扫描工具回显完整凭据** —— 工具输出会进日志与 CI artifact，本身成为泄露面。
5. **噪声太多导致漏看** —— 分隔线、路径、标识符必须过滤，否则报告不可用。
6. **文档示例用真实值改一半** —— `s****No` 这种"半脱敏"仍暴露首尾形态，应改为
   `<在仓库 Secrets 中配置>` 这类占位符。
7. **push 后才处理退役/脱敏** —— 已 push 的内容会留在远端历史；**清理必须在 push 前完成**。
8. **`filter-repo` / BFG 属于破坏性操作** —— 重写历史会改变 commit hash、影响所有协作者与
   已 fork 的仓库，**必须先获得明确授权**，不得自行执行。
